# iOS QA 스킬

각 부분은 개별적으로 올바르게 구현되어 있어도, 연결 지점(경계면)에서 계약이 어긋나 발생하는 버그를 찾기 위한 방법론.

## 핵심 통찰: 빌드 성공 ≠ 정상 동작

`xcodebuild build`가 성공했다고 런타임에 정상 동작하는 것은 아니다. Swift의 타입 시스템은 강력하지만 다음 경우 컴파일러가 경계면 버그를 잡지 못한다:
- `Codable`의 `CodingKeys`가 실제 서버 응답 필드명과 다를 때 (컴파일은 되지만 디코딩 실패 또는 조용한 nil)
- 강제 언래핑(`!`)이나 `try!`로 우회된 안전성 (런타임 크래시로만 드러남)
- `Any`/제네릭 캐스팅으로 타입을 우회한 경우
- 즉시 반환값과 비동기 콜백 결과의 shape이 다른데 프론트에서 구분하지 않는 경우

정적 코드 리뷰나 빌드 성공만으로는 이런 결함을 잡을 수 없다 — 반드시 **양쪽을 동시에 읽는** 교차 비교가 필요하다.

## 프로젝트 컨벤션 확인 (가장 먼저)

프로젝트 `CLAUDE.md`의 `## 프로젝트 컨벤션`을 먼저 읽는다. 값 대신 기존 아키텍처 문서의 경로/링크만 있으면 그 문서를 `Read`로 열어 확인한다. 컨벤션 섹션 자체가 없으면 저장소에 이미 아키텍처 문서가 있는지 먼저 찾는다(`docs/ARCHITECTURE.md` 등). 아래 "경계면 교차 비교 표"와 `references/boundary-checklist.md`는 SwiftUI+MVVM을 기준으로 작성되어 있다 — 프로젝트가 TCA/UIKit/Clean Architecture 등을 쓴다면 항목을 그대로 대입하지 말고 대응 개념으로 치환해서 적용한다 (예: TCA면 `@Published` 대신 Reducer의 `State`, 네비게이션 대신 `Reducer`의 destination case; UIKit이면 View 바인딩 대신 `IBOutlet`/delegate 데이터 흐름; 모듈화 프로젝트면 모듈 간 의존성 규칙 위반 여부도 함께 확인). 빌드/테스트 명령도 Tuist 프로젝트라면 `tuist build`/`tuist test`로 대체될 수 있다.

## 검증 절차

1. **빌드 실행** — `xcodebuild build`(또는 `swift build`)를 실제로 실행해 성공을 확인한다. 실패 시 원인을 정확히 짚어 보고한다.
2. **테스트 실행** — `xcodebuild test`(또는 `swift test`)를 실행해 기존/신규 테스트 통과 여부를 확인한다.
3. **경계면 교차 비교** — 아래 표의 각 항목에 대해 생산자 코드와 소비자 코드를 함께 Read한다.
4. **정적 위험 패턴 검색** — `grep`으로 강제 언래핑, `try!`, `as!` 사용처를 찾아 정말 안전한지 개별 판단한다.

## 경계면 교차 비교 표

상세 체크리스트는 `references/boundary-checklist.md`를 참조한다. 핵심 4개 경계면:

| 경계면 | 왼쪽 (생산자) | 오른쪽 (소비자) | 자주 나오는 불일치 |
|--------|-------------|---------------|------------------|
| View ↔ ViewModel | `@Published`/`@State` 프로퍼티명·타입 | View의 바인딩(`$viewModel.x`) | 프로퍼티 리네임 후 View 미갱신 |
| API 응답 ↔ 모델 | 서버 JSON 필드명 | `Codable` struct `CodingKeys` | camelCase/snake_case 불일치 |
| 네비게이션 | 실제 정의된 화면/enum case | `NavigationLink`, `.sheet(item:)`, `NavigationPath` push 값 | 존재하지 않는 case로 이동 시도 |
| 상태 전이 | enum 상태머신에 정의된 전이 | 실제 상태 변경 코드(`self.state = ...`) | 중간 상태에서 최종 상태로의 전환 누락 |

## 검증 방법: "양쪽 동시 읽기"

한쪽만 읽고 "정의되어 있으니 괜찮다"고 판단하지 않는다. 예를 들어 API 클라이언트 검증 시:

```
1. NetworkClient/APIService의 응답 디코딩 코드에서 실제 Codable 타입 확인
2. 해당 API를 호출하는 ViewModel/Repository의 사용 지점 확인
3. 서버가 실제로 반환하는 JSON 구조(스펙 문서 또는 샘플 응답)와 CodingKeys 비교
4. 옵셔널 처리가 양쪽에서 일관되는지 확인 (서버가 nullable인데 모델이 non-optional이면 디코딩 실패)
```

## 검증 우선순위

1. **통합 정합성** (최우선) — 런타임 크래시/오동작의 주요 원인
2. **기능 스펙 준수** — 요구사항 대비 구현
3. **코드 품질** — 강제 언래핑 남용, 경합 상태, 미사용 코드

체크리스트는 "존재하는가?"보다 "일치하는가?"를 묻는 형태로 작성한다. "API가 존재하는가"보다 "API 응답 shape과 호출부의 기대가 일치하는가"가 실제 버그를 잡는 질문이다.

## 점진적 QA

기능 전체가 끝난 뒤 한 번에 검증하지 않는다. 모듈(화면/API 하나)이 완성되는 즉시 해당 범위만 검증해, 초기 경계면 불일치가 후속 모듈로 전파되기 전에 잡는다.

## 리포트 형식

```markdown
## 통과
- {항목}

## 실패 (경계면)
- {파일:라인} — {불일치 내용} — 제안: {수정 방향}

## 실패 (스펙)
- {항목} — {기대와 다른 점}

## 미검증
- {항목} — {검증 불가 사유, 예: 시뮬레이터 미실행}
```

> 상세 항목별 체크리스트: `references/boundary-checklist.md` 참조.
