# 기술 리서치 스킬

라이브러리/프레임워크/API에 대해 정확하고 출처가 명확한 조사 결과를 만들기 위한 절차. 학습 데이터에 있는 정적 지식은 라이브러리 버전이 올라가면 틀린 정보가 되기 쉽다 — 특히 API가 자주 바뀌는 라이브러리(TCA, Tuist, 서드파티 SDK)는 정적 지식에 의존하지 않고 매번 최신 문서를 조회해야 한다.

## 1. 조사 범위 특정

조사 요청이 모호하면(예: "이 라이브러리 조사해줘") 먼저 무엇이 필요한지 좁힌다: 라이브러리명 + 대략의 버전, 알고 싶은 구체적 API/기능, 조사 목적(신규 도입 검토 vs 기존 코드 마이그레이션 vs 특정 에러 해결).

## 2. context7 우선 조회

1. `mcp__context7__resolve-library-id`로 라이브러리 ID를 먼저 찾는다. 이름이 모호하면 후보가 여러 개 나올 수 있다 — 설명과 버전을 보고 실제 요청과 가장 일치하는 것을 고른다.
2. `mcp__context7__query-docs`로 실제 문서를 조회한다. 질문을 구체적으로 좁혀서 질의할수록(예: "SwiftUI 통합 방법" 대신 "@Dependency로 URLSession 주입하는 방법") 관련성 높은 결과를 받는다.
3. 한 번의 조회로 충분하지 않으면 후속 질의를 이어간다 — 첫 조회 결과에서 나온 개념(예: 특정 프로토콜명)을 다시 질의해 깊이 파고든다.

## 3. context7로 부족할 때: 웹 검색 보완

다음 경우 `WebSearch`/`WebFetch`로 보완한다:
- `resolve-library-id`가 대상을 찾지 못함 (아직 색인되지 않은 라이브러리, 사내 프레임워크 등)
- Apple 퍼스트파티 프레임워크처럼 context7의 커버리지가 약한 대상 — `developer.apple.com`의 공식 문서, WWDC 세션 노트를 우선 조회한다
- 특정 에러 메시지에 대한 알려진 이슈/해결법 조사 — 라이브러리의 GitHub Issues, CHANGELOG를 조회한다
- 라이브러리 선택(여러 후보 비교)을 위한 커뮤니티 동향(유지보수 활성도, GitHub star/issue 추이 등)

## 4. 출처 기록 원칙

모든 조사 결과에는 근거를 남긴다: 문서 URL, 조회 시점 기준 라이브러리 버전. "확인함"이라고만 쓰지 않고 어디서 확인했는지 명시해야, 나중에 API가 바뀌었을 때 무엇을 다시 확인해야 하는지 추적할 수 있다.

## 5. 조사하지 않아도 되는 것

표준 언어/프레임워크의 잘 알려진 동작(예: `Array.map`의 동작, SwiftUI `VStack`의 기본 정렬)처럼 정적 지식으로 충분히 정확하게 답할 수 있는 질문은 조사 대상이 아니다. 조사는 "최신성이 실제로 답의 정확도를 좌우하는 경우"에 집중한다 — 불필요한 조회는 시간과 컨텍스트를 낭비한다.

## 리포트 형식

```markdown
## 요약
{한 문단 — 무엇을 조사했고 핵심 결론은 무엇인지}

## 핵심 내용
{API 사용법, 설정 방법 등 — 항목별로}

## 코드 예시
{실제 동작하는 예시 — 문서에서 가져온 것이면 그대로, 각색했으면 각색했다고 명시}

## 출처
- {문서명/URL} (버전: {x.y.z}, 조회일: {날짜})

## 대안 비교 (해당 시)
| 옵션 | 장점 | 단점 | 이 프로젝트에 적합한가 |
|------|------|------|---------------------|
```
