# iOS 개발 문서 작성 스킬

코드를 읽고 정확하게, 그리고 "왜"를 중심으로 문서를 작성하기 위한 가이드.

## 문서 유형별 목적

| 유형 | 목적 | 위치 |
|------|------|------|
| README | 프로젝트 개요, 빌드/실행 방법, 새 팀원 온보딩 | 저장소 루트 |
| 아키텍처 개요 | 모듈 구성, 데이터 흐름, 주요 결정과 이유 | `docs/ARCHITECTURE.md` |
| DocC 주석 | 공개 API의 사용법과 계약(전제조건/부작용) | 코드 내 `///` |
| CHANGELOG | 버전별 사용자 대상 변경 이력 | `CHANGELOG.md` |

## README 구조

```markdown
# {앱 이름}

{한 문단 개요 — 무엇을 하는 앱인지}

## 요구사항
- Xcode {버전}
- iOS {최소 배포 버전}

## 빌드 및 실행
{실제로 동작하는 명령/절차만 기술}

## 프로젝트 구조
{폴더 구성과 각 폴더의 책임 — 실제 구조와 반드시 일치}

## 아키텍처
{MVVM 등 채택한 패턴과 그 이유. 상세는 docs/ARCHITECTURE.md 링크}
```

빌드 방법은 실제로 실행해보고 검증한 명령만 적는다 — 동작하지 않는 명령이 적힌 README는 없느니만 못하다.

## DocC 주석 스타일

공개(public/open) API에 우선 작성한다. internal 구현 세부사항까지 전부 문서화하려 하지 않는다 — 유지보수 부담만 커진다.

```swift
/// 지정한 사용자 ID로 프로필 정보를 가져온다.
///
/// 네트워크 실패 시 `URLError`를, 사용자를 찾을 수 없으면
/// `UserRepositoryError.notFound`를 던진다.
///
/// - Parameter id: 조회할 사용자의 고유 ID
/// - Returns: 조회된 `User`
func fetchUser(id: String) async throws -> User
```

함수 시그니처를 그대로 문장으로 옮기는 주석("사용자 ID를 받아 User를 반환한다")은 정보 가치가 없다. 대신 **시그니처만으로 알 수 없는 것**(에러 조건, 부작용, 스레드 요구사항, 전제조건)을 적는다.

## 아키텍처 문서: Why 중심

아키텍처 문서는 구조를 나열하기보다, 왜 그 구조를 택했는지와 대안으로 무엇을 배제했는지를 기록할 때 가치가 커진다.

```markdown
## 상태 관리: MVVM + Combine

ViewModel이 상태를 소유하고 View는 렌더링만 담당한다.
Redux류 단방향 아키텍처 대신 MVVM을 택한 이유: 팀 규모 대비
보일러플레이트 비용이 낮고, SwiftUI의 @Published와 자연스럽게
통합되기 때문이다. 화면 간 공유 상태가 늘어나면 재검토한다.
```

## 코드-문서 정합성 유지

- 문서 작성/갱신 전 대상 코드를 실제로 읽는다. 요구사항 설명이나 커밋 메시지만 보고 문서를 쓰지 않는다.
- 기존 문서를 갱신할 때는 변경된 부분만 수정하고, 스타일과 무관한 섹션은 그대로 둔다.
- 코드 의도가 불명확하면 추측으로 단정하지 않고 "확인 필요" 표시를 남기거나 구현자에게 확인한다.
